# 「探す」のUWB暗号・トークン経路の静的調査

調査日: 2026-10-30。Androidアプリのみで標準の「探す」のiPhoneへ接続するための追加調査です。暗号処理の一部をダミー入力で再現できました。対象iPhoneとの接続、所有者トークンの取得、Galaxyでの距離・方向の実測は未達です。

## 取得物と検証範囲

| 取得物 | バージョン | SHA-256 |
| --- | --- | --- |
| iOS `nearbyd` | iPhone18,3 / iOS 27.0.1 / 24A446 | `4f2702b9e7ab26ac9aab305f15a054965690d40cd6a0e29a6dacdd818d6f0dfa` |
| iOS `CoreUtils` | 同じXcode DeviceSupportのarm64eシンボル | `c9283fc54c41cdd746c9d2c244a28ecf175f9ec9ab6a991f67e0595cbcc92f70` |
| macOS `/usr/libexec/findmylocateagent` | macOS 27.2 / 26B123、arm64eスライスを解析 | ファットバイナリ全体: `46a6157e0591725563e41a15ec9024d2ab0948d76be0f7bfc530ed010a55f4c1` |

以下のアドレスは、それぞれ上記ビルドの静的仮想アドレスです。別ビルドへ転用しません。OSデーモンは実行せず、Keychain、アカウントDB、実際のIRKは読んでいません。再現プログラムが呼ぶのは、ホストMacのCommonCrypto/CoreUtilsの純粋な暗号関数だけです。

## 1. セッション鍵

`NIServerNBAMMSSession._initializeEncryptionSessionIfNecessary` (`0x1002e4f18`) は8バイトの乱数を作り、`_sessionToken.getIRK` と一緒に `NIServerCryptoSession` の暗号化用インスタンスへ渡します。受信した相手のセッションIDには別の復号用インスタンスを作ります (`0x1002e4d40` 以降)。双方のIDを同一と決め打ちする構成ではありません。

`NIServerCryptoSession._deriveSessionKeyFromKeyDerivationKey:sessionIdentifier:` (`0x10029ac98`) の呼び出しは次の形です。

```text
sessionKey = HKDF-SHA256(
    IKM  = sessionToken.getIRK(),
    salt = empty,
    info = sessionIdentifier の生バイト,
    L    = 32 bytes
)
```

CommonCryptoのdigest指定は数値10です。Apple公開ヘッダーの `kCCDigestSHA256 = 10` と、`CCKDFParametersCreateHkdf` の引数順で確認しました。32バイトという長さだけからSHA-256と推測したものではありません。[CommonDigestSPI.h](https://github.com/apple-oss-distributions/CommonCrypto/blob/main/include/Private/CommonDigestSPI.h)、[CommonKeyDerivationSPI.h](https://github.com/apple-oss-distributions/CommonCrypto/blob/main/include/Private/CommonKeyDerivationSPI.h)

## 2. 暗号メッセージの形式

`NIServerCryptoSession.encrypt:` (`0x100299be0`) と `decrypt:` (`0x10029a24c`) はAES-CCMを使用します。生成した32バイトの鍵、8バイトのnonce、6バイトの認証タグを渡しています。`CCCryptorCreateWithMode` のmode=12、algorithm=0はAppleの定義と照合しました。padding引数は実際の呼び出しどおり1000で再現しています。[CommonCryptorSPI.h](https://github.com/apple-oss-distributions/CommonCrypto/blob/main/include/Private/CommonCryptorSPI.h)、[CommonCryptor.h](https://github.com/apple-oss-distributions/CommonCrypto/blob/main/include/CommonCryptor.h)

| 位置 | 長さ | 内容 |
| --- | --- | --- |
| 0 | 1 | バージョン `01` |
| 1 | 4 | counter、little-endian |
| 5 | 6 | CCM認証タグ |
| 11 | 可変 | 暗号文 |

```text
nonce = uint64_le(counter)
AAD   = 01 || uint32_le(counter)
```

暗号化用counterは `arc4random_uniform(0xffff0000)` で初期化され、暗号化の前に増えます。`0xffffffff` 以降はそのまま暗号化を続けない分岐があります。ダミー検証ではcounterを固定していますが、実装時に固定nonce/counterを使ってよいという意味ではありません。

ここで分かったのは内部NBAMMSメッセージの暗号エンベロープです。BLEのmanufacturer dataやGATT特性へ、このバイト列をそのまま送れることは確認していません。無線上の完全なフレームや再送・再起動・リプレイ処理は別途調査が必要です。

## 3. 相互認証のchallenge/response

`_encryptAndUpdateMutualAuthPayload` (`0x1002e5ca0`) は、基本形として21バイトの平文を作ってから上記の暗号処理へ渡します。

| 位置 | 長さ | 内容 |
| --- | --- | --- |
| 0 | 1 | 基本message ID `01`。条件によりsignalling情報を埋め込む分岐あり |
| 1 | 1 | Finderのoutbound/inbound状態を上下4bitへ格納 |
| 2 | 3 | Finderのoutbound challenge |
| 5 | 6 | Finderのoutbound response |
| 11 | 1 | Findeeのoutbound/inbound状態を上下4bitへ格納 |
| 12 | 3 | Findeeのoutbound challenge |
| 15 | 6 | Findeeのoutbound response |

3バイトの乱数生成は `0x1002e60dc`、response生成は `0x1002e6a58`、受信responseの検証は `0x1002e6b60` です。生成ヘルパーは次の計算を行います。

```text
response = little_endian_bytes(
    SipHash-2-4(roleToken.IRK, outboundChallenge || inboundChallenge)
)[0:6]
```

検証ヘルパーはchallengeの順序を逆にし、受信responseと比較します。`_processPeerMutualAuthState` (`0x1002e6504`) は役割に応じた `_finderToken` / `_findeeToken` を選んでヘルパーへ渡します。暗号化用の `_sessionToken` と役割別トークンを混同しません。トークン同士の関係や配布手順を、この計算式だけで再現したとはしていません。

`CoreUtils._SipHash` (`0x18be3bcb0`) の定数、メッセージ圧縮2round、終端処理4roundを逆アセンブルで確認しました。単に関数名からSipHash-2-4と仮定したものではありません。検証プログラムでは、独立したPython実装をホストのCoreUtilsと入力長0〜63バイトで比較しています。

## 4. IRKからのアドレス計算と無線設定

`NIServerFindingRangingProvider._macAddressForIRK:` (`0x1002efbfc`) は、IRKをSipHash鍵とし、バイナリ内の固定8バイト `01 23 45 67 89 ab cd ef` を入力します。64bitの結果を返し、呼び出し元のサービス要求構造体にも64bitで保存します (`0x1002ee600`)。これを6バイトのBluetooth MACアドレスだとは扱いません。Android側のUWBアドレスに使う場合の意味・型・バイト順の対応は未確認です。

`_getDefaultNbammsRangingConfigParameters` (`0x1002efc54`) には次の内部設定があります。

| キー | 値・条件 |
| --- | --- |
| `nbPacketType` | `0x1001` |
| `mmsBandChannel` | 9 |
| `nbSlotSize` | 4 |
| `startTimeUncertainty` | 10,000,000 |
| `interval` | 99 |
| `enableNonInterlacedMMS` | false |
| `mmsSlotSize` | 72。`UseTestNbammsMode` の分岐で設定 |
| `napSlotSize` / `dataSlotSize` | 6 / 10 |
| `useType2Addr` | true |

単位やenumの対応が不明な値をAndroidのslot durationやFiRa config IDへ代入しません。`_prepareNbammsServiceRequestForDiscoveryToken:…` (`0x1002edd2c`) にはNBとMMSそれぞれの設定があり、16バイトのIRKも要求構造体へコピーします (`0x1002ee5d4` 以降)。このコピー先をAndroidのStatic STS IVやProvisioned STS keyと同じものだとは確認していません。

Android公式のiOS相互運用はAppleアクセサリープロトコル、`CONFIG_UNICAST_DS_TWR`、OOBで交換した一致する設定を前提とします。今回の標準「探す」のNBAMMSがそれと同じ無線方式であることや、Galaxyの公開APIから同じモードを選択できることは未確認です。[Android Ranging公式資料](https://developer.android.com/develop/connectivity/ranging#uwb-interoperability)

## 5. Mac版で見つかったトークン経路

`FindMyLocate` の `FriendshipProtocol` には `ownerToken()`、`peerToken(for:)`、`requestOwnerToken(force:)`、`startOwnerRanging()`、`startRanging(handle:)` があります。Macの `findmylocateagent` は次のクラス・フィールドを持っています。

- `NITokenService`: Account、CloudKit、DataManagerなどの状態stream、トークン更新task、`invalidSharedSecret` / `missingOwnerSharedSecret` などのエラー。
- `NIRangingService.Trampoline`: NISession、Finder/Findeeそれぞれのconfig data session。
- `RangingConfigDataSession`: peerHandle、ownerHandle、peerToken、NIFindingRole、NIConfiguration、peerDestination。
- `generateFindingDiscoveryTokenWithSharedSecret:` の参照、および `FindingConfigEnvelopeV1` / `FindingConfigSessionStopEnvelopeV1` を扱う処理の文字列。

さらに、トークン生成APIを呼ぶ実コードを `0x100404dac` の関数まで追いました。`FindMyCrypto.SharedSecretKey.data` をCryptoKitのSymmetricKeyへ変換し、次の導出結果を `generateFindingDiscoveryTokenWithSharedSecret:` へ渡します (`0x100405064`)。

```text
tokenInput = HKDF-SHA256(
    IKM  = SharedSecretKey.data,
    salt = UTF8("NITokenService.salt"),
    info = 空、または bucket.index の UInt64.data,
    L    = 16 bytes
)
```

分岐flag=1ではinfoを取らないCryptoKitオーバーロード (`0x100404f38`)、それ以外ではUInt64のdataをinfoに渡すオーバーロード (`0x100404fdc`) を呼びます。追加調査でmacOS 27.2のUInt64.dataは8バイトのlittle-endianと確認しました。[整数データの照合](UWB-DISCOVERY.md#5-トークン導出のbucket-indexのバイト順)を参照してください。実運用の更新間隔は未確定です。

| 呼び出し箇所・型 | 確認した内容 |
| --- | --- |
| `0x1003e4e30` | `OwnerSharedSecretRecord` がない場合のエラー分岐がある関数内。flag=1で導出 |
| `0x100403ec4` / `0x100408b14` | bucketからindexを読み、flag=0で導出。後者には `incomingSharedSecret` がない場合の分岐 |
| `OwnerSharedSecretsRecord` | id、type、sharedSecret、baseDateを保持 |
| `FriendSharedSecretsRecord` | incoming/outgoingそれぞれのsharedSecretとbaseDateを保持 |
| `DiscoveryToken.Bucket` | baseDate、UInt64のindex、dateIntervalを保持 |
| `FindingTokenEnvelopeV1` | serverId、baseDate、sharedSecretのDataを保持 |

この16バイトの導出と、先に説明したnearbydの32バイトのセッション鍵導出は別の段階です。アカウントのパスワードやWebのdevice IDをHKDFへ直接渡す実装にはしません。共有鍵レコードがどう正規に生成・配送されるかを調べる必要があります。

これは「人を探す」の関係性や設定配布に関係する経路です。自分のiPhone、ファミリーのデバイス、アクセサリーについて同じ鍵を取得できることや、iCloud Webのログインだけで利用できることを示してはいません。Macのこのコードの存在も、Mac本体でUWB測距できる証拠ではありません。

## 再現と検証結果

```bash
python3 tools/verify_uwb_crypto.py \
  --output research/uwb-ios27/synthetic-vectors.json
```

macOS上で追加パッケージなしに実行できます。入力はスクリプトに固定した公開ダミー値だけで、アカウントの鍵やファイルを引数に取る機能はありません。

| 検証 | 結果 |
| --- | --- |
| Python SipHash-2-4とホストCoreUtils、入力長0〜63 | 64件一致 |
| CommonCrypto AES-CCMとRFC 3610 packet vector 1 | 一致 |
| Python HKDF-SHA256とホストCommonCrypto | 一致 |
| Mac版のsaltを使う16バイトのHKDF導出とホストCommonCrypto | 一致 |
| ダミー相互認証平文の暗号化・復号 | 一致 |
| 32バイトのエンベロープを各位置1バイトずつ改ざん | 全32件を拒否 |
| 別の共有鍵での検証 | 拒否 |

CCMの独立した既知入力は [RFC 3610](https://www.rfc-editor.org/rfc/rfc3610)、SipHashの既知入力は [原著者のテストベクター](https://github.com/veorq/SipHash/blob/master/vectors.h) で照合しました。ホストの暗号関数の検証であり、iOSデーモンを実行して得た実機通信のキャプチャではありません。

ダミー入力 `IRK=00…0f`、`sessionIdentifier=10…17` では、導出鍵は `7804b64218d58ff5d786486e71c480f61acbaf036ece66c672d9a976ad6178d2` です。この値はテスト専用で、本人の鍵ではありません。fixtureは簡単にするため役割別IRKとsession IRKを同じ値にしており、実際のトークン選択や状態遷移を証明するものではありません。

## 次に詰める点

1. 標準「探す」の対象別に、認証済みの所有者が必要なトークンを取得する経路を特定する。「人」「自分のデバイス」「アクセサリー」の経路を区別する。
2. CBSpatialInteractionSessionとNBAMMSへの入力から、探索・設定配布・暗号メッセージが実際の無線へ載る手順を追う。
3. NBAMMSの無線設定とGalaxyの公開UWB APIの対応を確認する。公開FiRaモードと一致する前提を置かない。
4. 対応が確認できた方式でセッション開始と実測コールバックを検証する。

今回、アプリのUWB機能追加やAPKの更新はしていません。サウンド送信や対象への無線コマンドも実行していません。
